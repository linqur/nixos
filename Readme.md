# NixOS-конфигурация

Воспроизводимая домашняя система: одна конфигурация даёт одинаковый результат на любом устройстве.

## Принципы

1. **Только нужное.** Включено только то, чем я реально пользуюсь. Остальное выключено или работает в минимальном режиме.
2. **Не используется — не потребляет.** Никаких автозагрузок, предзапусков и фоновых проверок по умолчанию. Медленный холодный старт допустим.
3. **Исключения — осознанные.** Автозапуск включается вручную для конкретной программы, если я так решил.

## Приоритеты оптимизации

Если подходит несколько решений, выбираю по порядку:

1. **Безопасность и надёжность.** Инструмент и его настройки не должны увеличивать риск взлома, утечки, заражения или потери данных — это учитывается первым и обычно перевешивает остальные критерии.
2. **CPU / GPU — температура и ресурс.** Меньше нагрева и деградации, выше отзывчивость.
3. **Сеть — сначала стабильность, потом трафик.** Системные настройки стека (например, TCP BBR), экономия трафика — в настройках конкретных приложений.
4. **Диск (NVMe) — износ.** Меньше лишних записей.
5. **Память — объём потребления.**

Общее ограничение: оптимизация сети, диска или памяти не должна заметно нагревать компоненты.

## Хосты и профили

Всё, что относится к одной функции (niri, docker, initrd…), лежит в одном файле — вместе с отличиями между хостами.

- `hosts/<host>/` содержит только `profile.nix` (особенности железа), `disko.nix` (разметка) и `configuration.nix` (имя хоста).
- `profile.nix` — данные, без настроек: значения из `lib/enums.nix` и параметры вроде экрана. Попадает в модули NixOS и Home Manager аргументом `profile`.
- Модуль сам решает, что делать на конкретном железе: `lib.mkIf` / `lib.optionals` по полям профиля. Часть функции в `hosts/` не выносится.
- Новое отличие между хостами — новое поле профиля (и значение в `enums`, если это выбор из вариантов), а не новый файл в `hosts/`.
- Исключение — `vm-minimal`: та же VM, что `vm` (`profile.nix` и `disko.nix` импортируются оттуда), но без `nixos/imports.nix`. Только загрузчик, initrd, сеть и пользователь; нужные модули перечислены прямо в его `configuration.nix`.

## Скрипты (`scripts/`)

- `scripts/` (корень) — только точки входа: то, что готово запускать прямо сейчас. Интерпретируемые скрипты (`gpu-uv.py`) и собранные бинарники (`wgamma`) лежат здесь как есть.
- `scripts/src/` — исходники и вспомогательные ресурсы, которые сами не запускаются (Cargo/Go-проекты и т.п.).
- Бинарники коммитятся в git готовыми (бинарный blob), а не собираются Nix'ом из исходников при каждом rebuild — в отличие от `gpu-uv.py` (Nix лишь оборачивает текст в сборку с правильным python3+либами, это почти бесплатно) и общего принципа «собирается из исходников». Компромисс осознанный: немного места в репозитории против компиляции и сети (crates.io/модули) на каждый `nixos-rebuild`; скрипты маленькие — трейдофф оправдан.
- Правка: меняю исходник в `scripts/src/<name>/`, пересобираю руками, кладу результат в `scripts/<name>`, коммичу оба изменения. Nix-модуль, который его использует, просто копирует файл в store (`pkgs.runCommandLocal` + `install -Dm755`), без компиляции — см. `home-manager/modules/niri.nix` (`wgamma`).
- Бинарники только статические под musl: всё внутри, ни интерпретатора, ни путей к glibc в store. Сборка под gnu зашивает путь к конкретной glibc; после `nix flake update` и GC её может не стать, и бинарь перестанет запускаться. Цель musl задана в `.cargo/config.toml` проекта, поэтому сборка — обычный `cargo build --release && install -m755 target/x86_64-unknown-linux-musl/release/<name> ../../<name>`. Проверка: `readelf -d scripts/<name>` — без `NEEDED`. Строки `/nix/store/…-rust-default-*/…/library/…` внутри — пути исходников std в сообщениях о панике, файлы не открываются.

## Rust (`nixos/rust.nix`)

Тулчейн — официальные сборки rust-lang.org через `rust-overlay`, версия закреплена в `flake.lock`: один пакет `pkgs.rustToolchain` (cargo, rustc, clippy, rustfmt, rust-analyzer, `rust-src`), его же берут helix и VS Code. Сейчас stable с целями `x86_64-unknown-linux-gnu` и `x86_64-unknown-linux-musl`; новая цель — строка в `targets`. rustup не используется: `rust-toolchain.toml` чужих проектов игнорируется, другой тулчейн (nightly, MSRV) при необходимости добавляется отдельной командой-обёрткой.

## Загрузка: UKI + Secure Boot (`nixos/loader.nix`)

Без systemd-boot и без меню. На каждый `switch`/`boot` `uki-install` собирает UKI поколения, подписывает своими ключами sbctl (`/var/lib/sbctl`) и кладёт в `\EFI\BOOT\BOOTX64.EFI`. Откат конфигурации — через git; на ESP только два файла:

- `EFI/BOOT/BOOTX64.EFI` — последнее установленное, на него ведёт запись «NixOS» в NVRAM.
- `EFI/last-good.efi` — последнее успешно загрузившееся (дошло до `multi-user.target`, юнит `uki-mark-good`).

Оба защищены от GC gcroot'ами `/nix/var/nix/gcroots/uki/{default,good}`: `nix-collect-garbage -d` их не ломает. Подробности и обоснование — `tasks/uki.md`.

**BIOS, по порядку:**

1. Пароль на BIOS — обязательно: без него физический доступ = выключить Secure Boot.
2. Secure Boot → Clear Secure Boot keys (Setup Mode). Без этого `install.sh` прерывается до разметки.
3. `install.sh`: установка, `sbctl verify`, `sbctl enroll-keys --tpm-eventlog` (свои ключи + хеши option ROM этого железа, без Microsoft), запись «NixOS» в NVRAM (позиция — `bootOrder` в профиле).
4. Перезагрузка, Secure Boot включить, если выключен; проверить `sbctl status`.

- Каждая установка генерирует новые ключи → переустановка всегда начинается с Clear keys.
- **После обновления BIOS или vBIOS** хеши option ROM меняются: Clear keys → загрузка без SB → `sudo sbctl enroll-keys --tpm-eventlog`, иначе после включения SB может не быть изображения.

**Восстановление:**

1. Новое поколение не загрузилось → в UEFI «загрузка из файла» → `EFI/last-good.efi`; починить в git, rebuild.
2. Не помогло → установочная флешка NixOS. Ключи SB лежат на диске и не меняются, enroll не нужен:
   1. BIOS (пароль) → Secure Boot выключить → загрузиться с флешки (F8).
   2. `sudo cryptsetup open /dev/<корень> root`, `sudo mount /dev/mapper/root /mnt`, `sudo mount /dev/<ESP> /mnt/boot`.
   3. Поправить файлы прямо в `/mnt` и/или собрать новое поколение:
      - поверх, nix'ом флешки: `sudo nixos-install --root /mnt --flake <путь к репо>#<host> --no-root-passwd`;
      - или изнутри системы: `sudo nixos-enter --root /mnt`, затем `nixos-rebuild boot --flake …`.

      В обоих случаях `uki-install` с диска подписывает новый `BOOTX64.EFI` ключами из `/mnt/var/lib/sbctl`.
   4. Перезагрузка → BIOS → **Secure Boot включить обратно** → в системе `sbctl status`.
3. Ключи потеряны или ничего не помогло → переустановка (Clear keys, `install.sh`). Почему нет `rescue.efi` — `tasks/rescue.md`.

## Что помнить при правке конфига

Работа, которую NixOS по умолчанию делает на каждой загрузке, перенесена на сборку. Цена — несколько правил.

**Компромисс.** NixOS по умолчанию заново утверждает поколение на каждой загрузке: ручная правка, удалённый файл, откат — всё чинится перезагрузкой. Перенос на сборку или на смену поколения это самолечение отключает. Upstream (Perlless/Bashless Activation, NixOS/nixpkgs#267982, #428908) делает похожее ради безопасности и малого closure, а не скорости; общего переключателя «каждая загрузка / один раз при смене поколения» нет.

- Схема «один раз при смене поколения»: юнит запускается, только если `/run/booted-system` не совпадает с сохранённой меткой. Сравнение — на равенство путей, а не номеров, тогда откат на старый UKI тоже вызовет запуск. `ConditionNeedsUpdate=` из systemd не подходит: завязан на `/usr`, которого в NixOS нет.
- Прежде чем переносить что-то ещё — замерить (`systemd-analyze blame`, `critical-chain`). С nixos-init на загрузке почти ничего не осталось; выигрыш в миллисекундах не стоит потери самолечения.

### Home Manager активируется только при смене поколения (`nixos/home-manager.nix`)

- Файлы в `~`, которыми управляет Home Manager, при загрузке не восстанавливаются. Удалил или правил руками — вернёт только rebuild с изменениями в Home Manager.
- Приложение может подменить симлинк своим файлом (VS Code — `settings.json`, GTK-программы — свои настройки). Такой файл живёт до следующего изменения Home Manager.
- Принудительная активация: `rm ~/.local/state/home-manager/gcroots/current-home && sudo systemctl restart home-manager-linqur`.

### nixos-init, overlay `/etc`, userborn (`nixos/init.nix`, экспериментально)

- **`system.activationScripts` молча не выполняются.** При добавлении модуля или flake-входа (sops-nix, agenix и т.п.) проверить, не работает ли он через activationScripts: `grep -o 'snippet [^:]*' result/activate`. Сейчас там только то, что nixos-init/userborn/overlay покрывают сами.
- **Не править `/etc` руками.** Правка ложится в верхний слой overlay и перекрывает версию из всех следующих сборок. Всё — через `environment.etc`.
- **В chroot (`nixos-install`, `nixos-enter`) пользователей нет**: userborn создаёт `/etc/passwd` только юнитом при загрузке (NixOS/nixpkgs#408507). `install.sh` запускает его вручную перед `passwd`; ставить без него — `passwd: cannot determine your user name`.
  Удаление `init.nix` из импортов эту ошибку «лечит» не из-за nixos-init: вместе с ним выключается userborn, и пользователей в chroot создаёт старый `update-users-groups.pl`.
- Первое включение (и откат на поколение без него) — через `nixos-rebuild boot` + перезагрузку, не `switch`. При проблеме — `last-good.efi` (см. «Загрузка»).
- **Включение на уже установленной без него системе теряет пароли.** Overlay закрывает прежний `/etc`, верхний слой `/.rw-etc/upper` пуст — userborn создаёт базы заново с заблокированными паролями. Либо переустановка через `install.sh`, либо до перезагрузки перенести `passwd`/`group`/`shadow` в `/.rw-etc/upper`.
- **`switch` на живой системе (NixOS/nixpkgs#480020: «no such user» во время `switch`).** Проверено в VM на nixpkgs `a033e66`: `switch` с изменением `/etc` (шрифт) и пользователей (убрана группа) + перезагрузка — чисто. У автора issue `users.mutableUsers = false`, у нас `true`. Гипотеза по коду модуля userborn, не доказана: при `false` `/etc/{passwd,group,shadow}` — ro bind-mount'ы, которые userborn снимает и ставит заново, пока скрипт перемонтирования `/etc` переносит вложенные точки монтирования на новый overlay. При `true` этой ветки нет.
  Перед переходом на `mutableUsers = false` и после обновления nixpkgs — повторить тест в VM со снапшотом диска.

### NVIDIA: ядро из stable, драйвер из unstable (`nixos/nvidia.nix`)

В stable новые ветки драйвера не переносят: в 26.05 драйвер застрял на 595.x, а `_latest` ушло на 7.2+, где он не собирается. В unstable драйвер догоняет ядро примерно за месяц. Поэтому ядро берётся `linuxPackages_latest` из stable, а драйвер собирается из исходников отдельного входа `nixpkgs-nvidia` (ветка `nixos-unstable`) под это ядро.

- **Цена:** модуль NVIDIA собирается локально при каждом обновлении ядра (несколько минут), его нет в кэше.
- **Окно несовместимости:** новая ветка ядра появляется в stable раньше, чем драйвер из unstable её поддерживает (так было с 615.71 на 7.3). Сборка падает до активации — система не ломается, обновление блокируется.
- Без NVIDIA (VM) ядро остаётся `_latest` из `nixos/kernel.nix`: фиксация ядра описана в `nvidia.nix`.

**Рычаги.** Пока оба в положении «latest», конфиг на русле. Отклонение пишет `warning` на каждой сборке.

- Ядро: `kernelPin` в `nixos/nvidia.nix` — `null` (`_latest`), `"7_2"` (ветка, получает исправления), `"lts"`.
- Драйвер: `nixpkgs-nvidia.url` в `flake.nix` — `github:NixOS/nixpkgs/nixos-unstable` или `github:NixOS/nixpkgs/<rev>`. Предупреждение срабатывает, когда rev этого входа не совпадает с `nixpkgs-unstable`.

**Сборка упала после `nix flake update`** — откатывать нечего, понять, что сдвинулось:

1. Ветка ядра в имени `nvidia-open-<драйвер>-<ядро>` отличается от `uname -r` → `kernelPin = "<текущая ветка>"`.
2. Обновился драйвер → закрепить вход на прошлый rev: `git show HEAD:flake.lock | nix run nixpkgs#jq -- -r '.nodes."nixpkgs-nvidia".locked.rev'`.
3. Некогда разбираться → `git restore flake.lock`, обновление откладывается целиком.

**Собралось, но сломалось в работе:**

1. `last-good.efi` из UEFI (см. «Загрузка») или `nixos-rebuild switch --rollback`.
2. Что изменилось: `nix store diff-closures /run/booted-system /nix/var/nix/profiles/system | grep -E 'linux|nvidia'`.
3. Закрепить изменившийся компонент рычагами выше. Если сдвинулись оба — начать с драйвера.

**Возврат на русло:** `kernelPin = null`, url → `nixos-unstable`, `nix flake update nixpkgs-nvidia`. При каждом обновлении сначала пробовать `nixos-rebuild build` без фиксаций.

**Ограничения.**

- Ветки ядра без LTS удаляются из nixpkgs через ~3 недели после выхода следующей. Тогда `kernelPin = "7_2"` ломает eval — пора вернуться на `_latest` или уйти на `"lts"`.
- Фиксация ветки не помогает при регрессии внутри неё (7.2.9 → 7.2.10): тогда `"lts"` или временно закрепить весь `nixpkgs` на rev.

## Виртуалка для проверок

VM `nixos-vm` в session-libvirt пользователя `virtjail` (`nixos/virt.nix`), хост `vm` из flake. Сама VM — состояние, не конфиг: в Nix её нет.

- UEFI + Secure Boot в Setup Mode (под `sbctl enroll-keys`), q35, virtio-диск (`/dev/vda`), passt, virtiofs `/srv/virt/share` → тег `share`.
- Пул `default` создан вручную в `/var/lib/virtjail/.local/share/libvirt/images`: virt-install ищет пул в `$HOME` клиента, а демону с `ProtectHome` туда нельзя.
- **niri требует virgl**: видео virtio с `accel3d=yes` и SPICE `gl` с render node Intel по `/dev/dri/by-path/pci-0000:00:02.0-render` (`renderD*` перенумеруется, когда вернётся драйвер NVIDIA). Без этого niri отказывается от программного рендера, работает без мониторов и держит клавиатуру — выглядит как полное зависание, хотя гость жив.
- Если гость «завис»: с хоста `virsh send-key nixos-vm KEY_LEFTCTRL KEY_LEFTALT KEY_F2`, `virsh screenshot`, загрузка vCPU через `virsh domstats --vcpu`.
- Снапшот перед рискованным `switch` — только диска при выключенной VM: `sudo -u virtjail qemu-img snapshot -c <имя> <qcow2>` (`-a` — откат). Встроенные снапшоты libvirt с UEFI-переменными в pflash не работают.
